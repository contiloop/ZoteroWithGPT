# Zotero AI Research Companion Protocol v1

Protocol v1 carries UTF-8 JSON between a client and the native Zotero companion. It supports a selected ChatGPT Web study flow that discovers a manually saved arXiv paper offline, reads its actual local PDF, and, after human authorization, saves passage-linked native Zotero annotations containing explanations, proofs, questions, or reference links.

This document defines the implemented wire contract. Installation and real-client validation are recorded separately in the connection and native-host validation documents; protocol conformance alone does not prove that a save is visible in the reader.

## Product and safety rules

- There is no fixed annotation count. Each save is one separately identified operation with its own result.
- Long annotation comments remain annotation comments. The companion does not move them into child notes.
- A separate child note is created or updated only by an explicitly authorized `create_note` or `update_note` request.
- Existing files and manual comments are preserved. `append` adds content after the current content; `replace` changes only the explicitly targeted annotation comment or child note after a revision check.
- The protocol has no delete, SQL, PDF mutation, shell, code execution, bulk-save, or automatic save-all-chat operation.
- Paper, annotation, and note content is untrusted display data. It must pass through the rendering port and is never treated as an instruction to execute.
- The companion does not require or accept a model API key.
- The selected local-study workflow does not download, import, or repair papers. New `inspect_arxiv` and `ensure_arxiv_pdf` requests return `unsupported_capability`. Their schema shapes remain only for historical journal results.

## File session

The user selects one dedicated `<BRIDGE_ROOT>` in Zotero. Read
`<BRIDGE_ROOT>/bridge-v1.json`, then its relative `statusFile`, then the
descriptor again. Require unchanged complete descriptors, bridge/protocol
version 1, matching `profileId` and `sessionId`, and status `enabled: true`.
Reject absolute or escaping paths; never choose sessions by modification time.

The descriptor supplies `requestDirectory`, `resultDirectory`, `statusFile`,
`requestSuffix`, `resultSuffix`, `maxRequestBytes`, `maxResultBytes`, and
`maxRequestsPerScan`. These are authoritative for the current session, not
client configuration. Zotero must be running to process requests.

Publish one complete UTF-8 request with an atomic create-only write to
`<BRIDGE_ROOT>/<requestDirectory>/<operationId><requestSuffix>`; never append
or overwrite. If staging is necessary, write a `.partial` sibling and rename
without replacement. Partial files are ignored. Poll only
`<BRIDGE_ROOT>/<resultDirectory>/<operationId><resultSuffix>` and require
matching protocol version and operation ID.

A missing result is not evidence of nonexecution. A changed descriptor or
disabled status stops that session. Reconnect does not authorize copying pending
writes to new identities. Keep an uncertain mutation's original ID/payload and
follow the recovery rules below.

## Dedicated MCP adapter

The selected ChatGPT route exposes the thirteen active protocol operations plus
`zotero_get_operation_result` as fourteen fixed MCP tools. The lookup tool reads
a recorded request/result from the caller-supplied exact session, profile, and
operation identity; disabled historical sessions are read-only. It never
publishes a pending operation or substitutes a new ID.

One monotonic deadline covers session opening, capability checks, mutation
preflight, create-only publication, waiting, and full-body comparison. The
default budget is 60 seconds and the configurable ceiling remains below the
120-second tunnel limit. An awaited filesystem syscall cannot be hard-cancelled,
so slow I/O may finish after the transport response; recovery still uses only
the original identity. The server reads at most 8 MiB per result and caps the MCP
envelope/stdio transport at 10 MiB. A lower native descriptor limit remains
authoritative. Oversize data is rejected explicitly and never truncated.

## Request envelope

Every request is a JSON object with these fields:

| Field | Type | Rule |
| --- | --- | --- |
| `protocolVersion` | `1` | Other values return `unsupported_version`. |
| `operationId` | string | Opaque, 1-128 ASCII characters, matching `^[A-Za-z0-9][A-Za-z0-9._-]{0,127}$`. |
| `operation` | operation name | Must be one of the operations below. |
| `profileId` | string | Required except for `connection_status`, which may use discovery without it. |
| `authorization` | object | Required for mutations and forbidden for reads. |
| `payload` | object | Operation-specific and strictly checked. |

Unknown envelope fields, unknown payload fields, invalid shapes, and invalid values are rejected before a mutation can run. `operationId` may be used to derive a filename only after validation; other request strings must never be used as filenames without an adapter-specific safe mapping.

Mutation authorization has this shape:

```json
{
  "kind": "explicit_request",
  "scope": "Save the full proof on the selected theorem in attachment ATTACH01."
}
```

`kind` is `explicit_request` when the human directly asked for the write or `approved_proposal` when the human accepted an assistant proposal. `scope` is nonempty human-readable text naming the approved content and target. This metadata records intent; it is not a signature or cryptographic proof. It does not replace target validation, revision checks, or anchor revalidation.

The maximum encoded request is 1,048,576 UTF-8 bytes. Query text is limited to 4,096 bytes, quoted passages and contexts to 65,536 bytes each, authorization scope to 16,384 bytes, and a saved comment or note body to 524,288 bytes. A value over a limit returns `too_large`; accepted saved content is never silently truncated.

The saved-body limit includes existing content, separators, and the addition for an append. Note HTML safety encoding also counts toward that limit. An over-limit append leaves the existing record unchanged.

Native annotation comments must already be in Unicode Normalization Form C (NFC) and must not begin or end with whitespace. Zotero's public annotation-comment setter applies `trim().normalize()`, so the extension rejects a comment before native mutation when that transformation would change the complete final body. Clients should remove only incidental transport or file-boundary whitespace, such as an editor-added terminal newline, and normalize the candidate to NFC before assigning the operation ID and recording authorization. They must preserve all substantive interior newlines, indentation, mathematics, and reference text. If either preparation step changes an already approved body, review and authorize the exact representable body and submit it as a new operation; do not silently trim meaningful content or reuse the prior identity.

Use a fresh operation ID for each new observation, including reads, status checks, and viewer verification. Reusing an ID returns its recorded historical outcome. Recover an uncertain write using the same ID and byte-equivalent payload. On startup, an interrupted durable `queued` operation becomes `rejected` with nonretryable `storage_error` explaining that it was never executed; it is not resumed. Only after that definitive non-writing result may the client re-read the target, obtain renewed mutation approval, and submit a new ID. An interrupted `running` operation requires native identity reconciliation and may remain `indeterminate`; never replace an unknown write with a new ID.

Recovery applies while a write has no terminal result, such as after a session
change during polling. Once an `indeterminate` result is terminal, replaying its
identity returns that historical result and does not run the mutation again.
Keep the identity and bounded native evidence for diagnosis. Do not infer that
an absent search result proves no commit, and do not use a new ID to recreate a
possibly committed record.

## Optional note content

Annotation comments retain their editable Markdown and LaTeX source. Optional child notes use Zotero note HTML and follow a separate content policy. Safe new paragraphs, lists, tables, code/preformatted blocks, and HTTP(S) reference links remain functional. Restricted Zotero links may select a library/group item or open its PDF with page/annotation parameters. Links do not load their destination automatically.

Unsafe resource elements in new content are displayed as escaped source instead of active elements. If the remaining content has unsafe destinations, ambiguous HTML, or another sanitizer difference, the complete original fragment is stored as escaped source in a readable preformatted block. The submitted characters remain readable without creating active images, frames, scripts, styles, or automatic network loads. Control characters that Zotero would strip are represented by replacement characters. Safety encoding counts toward the final saved-body byte limit.

Before DOM parsing, note HTML is limited to 64 nesting levels, 2,048 elements, and 65,536 aggregate raw tag characters. New over-budget content uses the escaped-original fallback; an existing over-budget body is unsupported for append. These HTML-work limits do not reduce the plain-text byte allowance.

An append preserves the existing native note body byte-for-byte and adds only the validated new fragment. If the existing body contains active resource markup, unsupported attributes, ambiguous structure, or content that Zotero would normalize destructively, the append is rejected before native mutation. Read the current note and use Zotero's editor to resolve that content, or explicitly approve a replacement; the companion never silently repairs existing rich content. The complete combined note, including the separator, must fit the saved-body limit.

## Primitive wire shapes

Page indexes are zero-based. A page range is inclusive at both ends:

```json
{ "startPageIndex": 0, "endPageIndex": 4 }
```

A range may contain at most 200 pages. A list `limit` is an integer from 1 through 100.

A native rectangle uses the coordinate values supplied by the Zotero/PDF reader boundary:

```json
{ "x1": 10, "y1": 20, "x2": 110, "y2": 34 }
```

All coordinates are finite and nonnegative, with `x2 > x1` and `y2 > y1`. A rectangle list contains 1 through 512 entries. Clients must preserve the adapter-provided native coordinate space. A client-supplied rectangle is only a locator candidate; its shape does not make it trusted geometry.

The native annotation colors supported by v1 are:

```text
#ffd400 #ff6666 #5fb236 #2ea8e5 #a28ae5 #e56eee #f19837 #aaaaaa
```

A resolved anchor has this shape:

```json
{
  "libraryId": "1",
  "itemKey": "ITEM1234",
  "attachmentKey": "ATTACH01",
  "attachmentFingerprint": "sha256:pdf-revision-a",
  "pageIndex": 2,
  "pageLabel": "3",
  "rectangles": [{ "x1": 12, "y1": 30, "x2": 140, "y2": 45 }],
  "selectedText": "posterior concentration",
  "matchEvidence": {
    "method": "exact_quote",
    "matchedText": "posterior concentration",
    "exact": true
  }
}
```

`matchEvidence.method` is `exact_quote`, `quote_with_context`, or `inspected_region`. Quote methods require `matchedText`; `exact_quote` also requires `exact: true`. `selectedText` is required for a highlight and optional for a region-linked note.

The anchor is still untrusted at the native write boundary. Immediately before writing, the native adapter must check the attachment fingerprint, parent and attachment identity, page, quote or inspected-region evidence, and rectangles against the current attachment. A changed fingerprint returns `stale_attachment` and requires resolution again. A missing or ambiguous match returns `unresolved_anchor`; the companion does not guess among geometries.

Revisions and attachment fingerprints are opaque snapshot tokens. Clients compare them for equality and do not interpret their contents.

## Operations

### `connection_status`

Payload: `{}`. `profileId` may be omitted for discovery.

Result fields: protocol version, plugin version, Zotero version, profile identity, enabled state, supported operations, annotation types, native colors, size capabilities, and transport description.

Only active operations appear in `capabilities.operations`. The core build
advertises thirteen operations, including `find_local_arxiv`; acquisition names
remain historical schema members and are not advertised.

### Retired acquisition

`inspect_arxiv` and `ensure_arxiv_pdf` are not advertised or executed. Their
request/result shapes remain in the v1 schemas for existing immutable history.
A terminal historical result may still be returned on exact identity replay;
a new acquisition request is rejected as `unsupported_capability`. Interrupted
old imports reconcile observed native identities without resuming acquisition.

### `find_local_arxiv`

Payload: `{ "url": "https://arxiv.org/abs/2401.01234v2", "limit": 25 }`. `limit` is optional, defaults to 25, and ranges from 1 through 100. The URL follows the strict official arXiv abstract/PDF grammar used by `inspect_arxiv`, including modern and legacy IDs, an optional positive version suffix, an optional terminal `.pdf`, and harmless query or fragment decoration. The extension normalizes the identity locally and performs no HTTP request.

This is an authorization-free profiled read across all eligible Zotero libraries. It never imports, writes, or selects a target. Its success data is:

```typescript
type LocalArxivIdentity = {
  arxivId: string;
  version: number | null;
};
type LocalArxivEvidence = LocalArxivIdentity & {
  attachmentKey: string | null;
  origin: "url" | "archive_id" | "extra" | "provenance";
  fingerprint?: string;
};
type FindLocalArxivData = {
  source: LocalArxivIdentity;
  matches: Array<{
    paper: PaperMatch;
    evidence: LocalArxivEvidence[];
  }>;
  truncated: boolean;
};
```

`source.version` is null for an unversioned URL. Parent evidence has a null attachment key. Returned children are PDFs, and attachment provenance is included only when its fingerprint equals that same attachment's current fingerprint. A PDF remains a candidate when hashing is unavailable, but it has no fingerprint-bound provenance. Parent metadata and parent provenance never establish a PDF version. Unknown versions remain unknown.

Conflicting IDs and versions remain visible. Native keys and identical evidence are deduplicated. Matches sort by library ID then item key; attachments by attachment key. Evidence sorts parent records before attachment records, then by origin (`url`, `archive_id`, `extra`, `provenance`), arXiv ID, null before concrete version, fingerprint, and attachment key. Strings use ascending JavaScript code-unit comparison, not locale collation. The operation returns at most `limit` matches and sets `truncated` exactly when more exist. More than 100 evidence records on one candidate returns `too_large` rather than an incomplete evidence set.

The selected workflow establishes a target only after this discovery and a fresh successful `read_pdf`. Missing, metadata-only, unreadable, ambiguous, truncated, conflicting, or explicit-version-mismatched results require a focused question or manual Zotero action followed by fresh calls. When the selected attachment has no current fingerprint, its bytes are inaccessible or unverified: stop before `read_pdf`, request manual file or path restoration, and continue only after fresh discovery returns a fingerprint. A later save may use the target retained in accessible conversation context, but it refreshes the session, fingerprint, passage, and revision evidence first. A failed explicit switch cannot fall back to the prior destination.

### `search_papers`

Payload:

```json
{ "query": "Bayesian inference", "limit": 25 }
```

`query` is nonempty and `limit` is optional. The result contains `matches`; each match gives `libraryId`, `itemKey`, title, creators, optional year, and attachment summaries. A match list is discovery data. It never implicitly selects a paper or attachment for a later operation.

### `read_pdf`

Payload:

```json
{
  "libraryId": "1",
  "itemKey": "ITEM1234",
  "attachmentKey": "ATTACH01",
  "pageRange": { "startPageIndex": 0, "endPageIndex": 4 }
}
```

The result gives `attachmentFingerprint`, opaque `attachmentRevision`, and `pages`. Each page contains zero-based `pageIndex`, visible `pageLabel`, full extracted `text`, quote `passageCandidates`, and inspected `regionCandidates`.

### `list_annotations`

Payload: `{ "libraryId": "1", "attachmentKey": "ATTACH01" }`.

The result contains native annotation keys, revisions, types, resolved anchors, optional selected text, comments, optional native colors, and deep links.

### `list_notes`

Payload: `{ "libraryId": "1", "itemKey": "ITEM1234", "limit": 25 }`. `limit` is optional.

The result contains child note keys, parent item keys, titles, and current opaque revisions. Listing notes does not select one for an update.

### `read_note`

Payload: `{ "libraryId": "1", "itemKey": "ITEM1234", "noteKey": "NOTE1234" }`.

The result contains the parent item key, note key, current revision, full content, and deep link.

### `resolve_anchor`

The common fields are:

```json
{
  "libraryId": "1",
  "attachmentKey": "ATTACH01",
  "fingerprint": "sha256:pdf-revision-a",
  "pageIndex": 2
}
```

Exactly one locator follows. A quote locator is:

```json
{
  "quote": {
    "exact": "posterior concentration",
    "prefix": "We next prove ",
    "suffix": " under regularity assumptions."
  }
}
```

An inspected-region locator is:

```json
{
  "inspectedRegion": {
    "rectangles": [{ "x1": 12, "y1": 30, "x2": 140, "y2": 45 }],
    "selectedText": "posterior concentration"
  }
}
```

The result is either `{ "status": "resolved", "anchor": ... }` or `{ "status": "unresolved", "reason": ..., "candidates": [...] }`. Candidate anchors are evidence for human inspection, not permission to choose automatically.

### `update_annotation`

This is an authorized mutation. A complete revision-checked append request is:

```json
{
  "protocolVersion": 1,
  "operationId": "op.annotation-revision-2026-10-21-01",
  "operation": "update_annotation",
  "profileId": "profile-A",
  "authorization": {
    "kind": "explicit_request",
    "scope": "After reading ANN00001 at rev:9, append the denominator detail to that annotation while preserving its existing comment."
  },
  "payload": {
    "libraryId": "1",
    "attachmentKey": "ATTACH01",
    "annotationKey": "ANN00001",
    "expectedRevision": "rev:9",
    "mode": "append",
    "comment": "Additional detail: the denominator bound uses positive prior mass in a Kullback-Leibler neighborhood."
  }
}
```

The result contains the key, new revision, complete saved comment, and deep link. `append` preserves the existing comment verbatim and adds the requested content. If the stored revision differs from `expectedRevision`, the adapter returns `conflict` without writing.

### `create_note`

This is an authorized mutation. Payload: `{ "libraryId": "1", "itemKey": "ITEM1234", "content": "Create this separate synthesis note because the researcher explicitly requested one." }`.

The result contains the child note key, revision, complete saved content, and deep link. This operation is never inferred from annotation length.

### `update_note`

This is an authorized mutation. Payload:

```json
{
  "libraryId": "1",
  "itemKey": "ITEM1234",
  "noteKey": "NOTE1234",
  "expectedRevision": "rev:9",
  "mode": "append",
  "content": "A new study question"
}
```

The result contains the key, new revision, complete saved content, and deep link. `append` preserves existing content. A stale `expectedRevision` returns `conflict` without writing.

### `verify_annotation`

Payload: `{ "libraryId": "1", "attachmentKey": "ATTACH01", "annotationKey": "ANN00001" }`.

The result reports two pieces of evidence: a storage readback and evidence from the actual Zotero PDF reader. Reading the storage record is not viewer confirmation. Viewer evidence must come from the reader integration.

## Response envelope

Every response has this exact top-level form:

```json
{
  "protocolVersion": 1,
  "operationId": "op.create-1",
  "state": "succeeded",
  "data": {},
  "error": null,
  "verification": {
    "storage": "confirmed",
    "viewer": "failed"
  }
}
```

`state` is `queued`, `running`, `succeeded`, `rejected`, `failed`, or `indeterminate`. `data` is an operation-specific object or `null`. `error` is `null` or `{ "code": string, "message": string, "retryable": boolean }`.

Both verification fields use `not_applicable`, `not_checked`, `confirmed`, or `failed`. A persisted write reaches `succeeded` only after storage readback is `confirmed`. Viewer confirmation is separate: a write with confirmed storage and failed viewer evidence remains `succeeded`, reports `viewer: "failed"`, and is not retried. If a possible native write has no confirmed readback, its state is `indeterminate` and the same operation must not be blindly executed again.

Error codes are:

```text
invalid_request unsupported_version unsupported_operation permission_denied
not_connected not_found ambiguous_target unresolved_anchor stale_attachment
conflict duplicate_id_mismatch unsupported_capability too_large storage_error
verification_failed unknown_outcome
```

For new acquisition requests, return `unsupported_capability`. Old outcomes
retain their recorded errors, including partial imports and unknown commits.
`retryable` never authorizes a new identity for a possibly committed mutation.

## Successful response data

The response schema defines closed, operation-specific data objects; there is no generic object fallback. The schemas retain fifteen historical operation shapes; thirteen are active:

| Operation | `data` shape |
| --- | --- |
| `connection_status` | `ConnectionStatus` |
| `inspect_arxiv` (historical only) | `InspectArxivData` |
| `ensure_arxiv_pdf` (historical only) | `EnsureArxivPdfData` with `completion: "ready"` on success |
| `find_local_arxiv` | `FindLocalArxivData` |
| `search_papers` | `{ matches: PaperMatch[] }` |
| `read_pdf` | `{ attachmentFingerprint: string, attachmentRevision: string, pages: PdfPage[] }` |
| `list_annotations` | `{ annotations: NativeAnnotation[] }` |
| `list_notes` | `{ notes: NoteSummary[] }` |
| `read_note` | `{ parentItemKey: string, noteKey: string, revision: string, content: string, deepLink: string }` |
| `resolve_anchor` | `{ status: "resolved", anchor: ResolvedAnchor }` or `{ status: "unresolved", reason: string, candidates: AnchorCandidate[] }` |
| `create_annotation` | `{ annotationKey: string, revision: string, deepLink: string, saved: SavedAnnotationSnapshot }` |
| `update_annotation` | `{ annotationKey: string, revision: string, comment: string, deepLink: string }` |
| `create_note`, `update_note` | `{ noteKey: string, revision: string, content: string, deepLink: string }` |
| `verify_annotation` | `{ annotationKey: string, storageEvidence: VerificationDetail, viewerEvidence: VerificationDetail }` |

Queued and running responses have null data and error. Rejected and indeterminate responses have null data and a protocol error. Failed responses normally have null data; the only retained failure data is the confirmed `ensure_arxiv_pdf` `item_only` shape with `storage_error`, storage `confirmed`, and viewer `not_checked`. This keeps a confirmed native parent visible without turning incomplete attachment evidence into a success.

The packaged schemas close structural shapes. Runtime parsers also enforce semantic joins including operation-specific result selection, canonical identity normalization, evidence-to-attachment ownership, provenance-to-current-fingerprint binding, capability-name uniqueness, and lifecycle cross-field rules. Schema validity alone does not establish those relationships.

## Identity, lifecycle, conflicts, and recovery

The canonical digest covers `protocolVersion`, `operation`, `profileId` when present, authorization when present, and the operation payload. It excludes `operationId`, because the durable identity is the pair of the opaque ID and this digest. Object keys are sorted recursively; array order is preserved; non-JSON values and nonfinite numbers are rejected. A digest adapter must apply a collision-resistant cryptographic hash to the canonical UTF-8 bytes.

An operation store atomically claims the ID and digest. The allowed lifecycle is:

```text
queued -> running -> succeeded | rejected | failed | indeterminate
queued -> rejected
```

The second path is only for a request rejected before execution. Terminal states are immutable. A second submission with the same ID and canonical request returns the durable prior state and result. The executor does not run again. Reusing the same ID with different request content returns `duplicate_id_mismatch` and leaves the historical record unchanged. Polling reads the durable record and never submits an operation.

Mutations are serialized per profile. There is no implicit atomic batch transaction across operation IDs.

`expectedRevision` is checked against the actual current target immediately before an update. A manual edit or sync update that changes the revision returns `conflict`; it is never overwritten. After a conflict, the client must read the target again and obtain renewed human approval for the updated content and target before sending a new operation ID.

The operation store is an adapter responsibility and must survive ordinary plugin reinstall or upgrade. A native adapter must associate a durable operation identity with a committed write so a crash-left `running` operation can be reconciled by inspection. Recovery inspects historical identity and native state; it never calls create again. A previously succeeded operation is returned from history even if a person later deletes its annotation. If commit status cannot be proven, recovery returns `indeterminate` with `unknown_outcome`.

The cut retains `protocolVersion: 1` for durable history. Historical acquisition
requests/results remain readable, but new acquisition execution is unsupported.
